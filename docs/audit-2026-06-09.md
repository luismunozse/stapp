## Resúmenes por área

### app/api/superadmin (all 58 routes)
Audited all 58 superadmin routes. Every single route correctly calls requireSuperadmin() as its first action and aborts on error before touching any data. The authentication perimeter is solid: the function relies exclusively on middleware-set headers (x-superadmin-panel, x-superadmin-email) that cannot be injected from outside because Next.js middleware overwrites them before any route handler runs. No route was found that bypasses this check. The dominant findings are a medium-severity header-injection trust boundary that is sound in production but fragile under certain deployment misconfigurations, one missing input validation in toggle-status, a null-userId blind spot in the sessions revoke route, and a potential double-subscription-payment issue in the renew flow. No cross-tenant data leaks or authentication bypasses were found.

### app/api/inventario, app/api/catalogo, app/api/conteos, app/api/depositos
73 route files audited. Auth and org-scoping are solid for the vast majority of routes: requireAuth/requireAdmin is called at every entry point, all main-table queries carry .eq("organization_id", organizationId), and stock mutations that matter (adjust_stock_atomic, transferir_stock_atomic, etc.) go through RPCs that pass p_organization_id and use SELECT FOR UPDATE. Four real issues found: one HIGH (cross-tenant stock/movement mutation via marcar-vencidos endpoint), one HIGH (missing inventory ownership check before inserting items_orden_compra in generar-oc), one MEDIUM (non-atomic absolute stock write in PUT /api/inventario/[id]), and one MEDIUM (full parsed.data passthrough to Supabase UPDATE in catalogo items PUT, allowing a client to link a cross-tenant inventario_id by bypassing the POST-only ownership check).

### app/api/public (22 routes), app/api/public/kiosco (1 route), app/api/kiosco (2 routes)
Audited all 25 public/kiosco API routes plus lib/public-token.ts. The core token-gating library (getOrderByPublicToken) is well-built: constant-time comparison, mandatory expiry check, null-token defense, fixed-length pre-filter. The kiosco admin routes (GET/POST/PUT/DELETE) are correctly guarded by requireAdmin(). The catalogo write surface has solid input validation, consent gates, and rate limiting on the two highest-risk endpoints (cupon/validar and upload). Four concrete issues found: one missing defense-in-depth guard on a PDF query, one unbounded payload on a mutation endpoint, two PII-over-HTTP-cache misconfigurations, and one missing token format validation on the public kiosco display route. No cross-tenant data leaks or auth bypasses were found.

### app/api/reportes, app/api/ordenes, app/api/cotizaciones, app/api/ventas, app/api/caja
Audited 57 route files across 5 API groups. Auth and org-scoping are generally solid: every route calls requireAuth/requireAdmin/requireAdminOrVendedor before DB access, and virtually every query carries .eq("organization_id", organizationId). Three genuine defects were found: one cross-tenant data leak in the P&L report via an unscoped pagos_venta query, one broken query-builder call in comparativa-ingresos that silently ignores the upper date filter, and one missing org_id column on manual repuesto inserts that could cause data integrity drift. The repuestos route also lacks role enforcement (any authenticated role can add parts to any order in the org). The orden-state-machine is consistently applied. No double-charge or RCE-class issues were found. N+1 patterns exist in top-clientes and estado-resultados but are bounded in practice.

### app/api/proveedores, app/api/clientes, app/api/tecnicos, app/api/vendedores, app/api/comisiones, app/api/ordenes-compra
Audited 31 route files across 6 API groups (approximately 2,400 lines). Auth is present on every route and org-scoping is applied correctly on most reads. The major failure pattern is routes that pre-verify ownership with a SELECT then issue the destructive write (UPDATE/DELETE) without repeating the organization_id predicate — leaving the write unscoped at the DB level. Three routes have this defect: clientes/[id] PUT and DELETE, and tecnicos/[id] DELETE and estado PATCH. Commission reversal paths (comisiones/pagar DELETE and comisiones/vendedores/pagar DELETE) have weaker guards than the pay path. A role-gap lets TECNICO users read vendedor commission data. The tecnicos/route.ts POST uses manual validation instead of Zod and its email-uniqueness check is cross-org. No cross-tenant IDOR was found in read paths; all SELECT queries carry organization_id. Ordenes-compra and proveedores groups are clean.

### app/api/subscriptions, app/api/subscription, app/api/mercadopago, app/api/rebill, app/api/webhooks (user-facing webhook CRUD), app/api/facturacion, app/api/pagos, app/api/reactivar-trial, app/api/onboarding, app/api/cron/subscription-sweep, app/api/cron/trial-management
Audited 20+ route files covering the full payment/subscription surface. The MercadoPago webhook signature verification and idempotency logic are solid and correctly fail-closed. The main concern is a single HIGH-severity idempotency gap in the Rebill payment webhook that can cause double-grant of premium access, plus two MEDIUM issues: a race condition in trial reactivation that allows slightly more than MAX_REACTIVATIONS under concurrent requests, and a fragile org-scoping approach in the facturacion list route that relies on a join filter rather than a direct organization_id column filter. No cross-tenant data leaks or auth bypasses found in this surface.

### app/api/auth (15 routes) + app/api/users (3 routes) + app/api/user (1 route)
Audited 19 routes covering registration, login (NextAuth v5 Credentials with email/password, Google ID Token, PWA refresh token), 2FA/TOTP lifecycle, password reset, email verification, session restore, and user profile/avatar/password management. Core auth logic in lib/auth.ts and lib/totp.ts. Audited 40+ route files across all specified groups. The cron layer is well-protected by requireCronAuth with a fail-closed design. Most authenticated routes follow the canonical pattern correctly. Four genuine defects were found: one CRITICAL (WhatsApp webhook accepts arbitrary POST payloads with no signature verification, enabling state mutation via spoofed Meta events), one HIGH (leads API exposes cross-tenant CRM data to any authenticated user and allows unscoped PATCH writes), one HIGH (export/reportes performs a server-side fetch to an internal URL constructed from the user-supplied `type` param, creating a blind SSRF/path-traversal vector), and one MEDIUM (import/execute accepts the full file as a base64 body with no size cap before parsing, enabling memory-exhaustion DoS). The subscription-sweep, lifecycle-email, and push routes are clean. The chatbot's in-process rate limiter is per-instance (not distributed) but is a low-severity operational concern, not a security defect.

### Multitenancy Isolation — Cross-org data leakage, IDOR, and unscoped delete operations in app/api routes
Reviewed ~40 [id] API routes plus the core auth/tenant infrastructure. The authentication foundation (requireAuth, validateUserTenant, middleware cross-tenant header check) is sound. The dominant pattern of pre-flight ownership check + org-scoped mutation is correct in most routes. However, four routes have the same class of defect: the final hard-delete operation drops the organization_id filter after a pre-flight ownership check, creating a real — if narrow — IDOR window. Two additional routes contain unscoped final-select fetches after mutation, leaking the response without org binding (low severity since the id is not attacker-supplied at that point). The garantias, caja, kiosco, vendedores, inventario, depositos, clientes, ordenes, and webhook routes are clean. No cross-tenant data leak was found in GET/read paths. All auth entry points correctly return organizationId from the JWT via requireAuth().

### supabase/migrations (200 files) — data-layer & schema integrity
200 migrations inspected across the full schema lifecycle. The core architecture (org scoping, plan limits, atomic sale/order functions) is solid. Three distinct classes of real defects were found: (1) a critical cross-tenant data-exposure via unenforced realtime anon policies that has never been revoked; (2) a widespread pattern in migrations 169–178 where "service-role-only" write policies are missing the TO service_role scope clause, making them open to all authenticated users and defeating tenant isolation on the entire inventory-extended module; (3) four tables that hold per-tenant PII/financial data with no RLS at all. The remaining issues are medium/low: a dead custom-setting RLS pattern, an open-to-all cotizacion_templates policy, and a `current_setting('role')` check that is not a reliable role guard in Postgres RLS. No double-charge or ENUM-mutation data corruption was found in the migration history; the prior tipo-filter bug on plans was already corrected (migration 113 targeted by slug, not tipo). The plan simplification (118) is clean.

### Scalability & Performance
Audited 250+ API routes, 9 cron jobs, 3 PDF generators, and core libs. The app has solid pagination on its main list endpoints (ordenes, inventario both cap at 100 rows with server-side count). The critical problems are concentrated in: (1) three cron jobs with severe N+1 query patterns that will degrade linearly with tenant growth, (2) a fully unbounded cross-tenant table scan in the lifecycle-emails cron, (3) synchronous heavy work (PDF generation + outbound logo HTTP fetch) inside request handlers with no timeout safety, and (4) an export route that makes a server-to-self HTTP fetch. No auth or multitenancy bypasses were found in this scope.

### Architecture & Maintainability
369 API routes across a Next.js 16 + Supabase + NextAuth v5-beta SaaS. The canonical auth/org-scoping pattern (requireAuth → org_id filter → plan limit) is consistently followed in the majority of routes. Critical infrastructure (requireCronAuth, requireSuperadmin, tenant validation) is sound. Three concrete security defects were found: one confirmed IDOR on the clientes DELETE endpoint, one pre-check/write split on sectores DELETE that relies on parent-chain ownership without direct org scope on the final write, and five routes that call raw auth() instead of requireAuth() thereby skipping tenant cross-validation. On top of those, two production dependency betas (next-auth 5.0.0-beta.30, react-signature-canvas 1.1.0-alpha.2) represent supply-chain and break-without-warning risk. The largest maintainability gap is 116 call sites using schema.parse() directly instead of the existing safeParseBody() wrapper — this means uncaught JSON parse errors throw unhandled exceptions on 73 of the 369 routes. Pagination boilerplate is duplicated across 24 routes (parsePagination() exists and is used in only 16 of them). No god-files at the lib level beyond the expected boundary (lib/auth.ts at 588 lines, lib/subscriptions.ts at 550 lines — both are cohesive, not god-files). The highest-leverage refactor is a withAuth/withOrg route wrapper that collapses the auth + tenant + org-id extraction into one HOC, cutting ~750 lines of repeated ceremony across the codebase.

### Security (cross-cutting) — authentication, multitenancy, uploads, webhooks, input validation, error handling
Reviewed middleware.ts (502 lines), lib/auth.ts, lib/auth-utils.ts, lib/superadmin-auth.ts, lib/rate-limit.ts, lib/image-magic-bytes.ts, lib/plan-limits.ts, lib/cron-auth.ts, lib/storage.ts, and ~25 API route handlers covering auth, uploads, payments, webhooks, leads, emails, and superadmin export. Four real defects found: one CRITICAL (WhatsApp webhook accepts unauthenticated writes that can auto-approve orders), one HIGH (leads routes lack org-scoping, leaking cross-tenant data), one MEDIUM (four upload routes skip magic-bytes validation), and one MEDIUM (DB error messages are exposed verbatim in 500 responses).
